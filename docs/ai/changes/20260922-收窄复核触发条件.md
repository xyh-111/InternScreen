# 2026-09-22 收窄复核触发条件（移除在读/学历）

## 目标

用户要求：**学历层次、是否在读都不需要人工复核**，复核只应关注院校层次（是否双一流）。

上一轮刚给复核弹窗补了「在读状态」「学历层次」两个选项，本轮按新口径把这两条复核路径整体去掉，
所以弹窗里的这两个选项也随之回滚。

## 用户确认的口径

| 口径 | 选择 |
|---|---|
| 收窄范围 | **B. 只移除「在读状态缺失」「学历层次缺失」两项**；时长 / 到岗天数 / 成都 / 置信度 / 边界 / AI 证据的复核全部保留 |

## 关键决策与风险

### 1. 缺失不再复核，而是直接淘汰（重要副作用）

移除这两个复核分支后，字段缺失不再被拦下，会**直接落到硬性条件**：

| 字段缺失 | 硬性条件判定 | 结果 |
|---|---|---|
| `in_school = None` | `not fields.get("in_school")` → 「非在读」 | 淘汰 |
| `degree_level = None` | `degree not in allowed_degrees` → 「非本科或研究生」 | 淘汰 |

即「抽不到」与「确实不符合」被当成同一件事。这正是用户选择 B 的预期代价。

### 2. 实测确认这个代价会真实发生

丙（`bing_zhang.txt`）原文明确写着「2024 级硕士研究生（在读）」，但实测：

```
跑图:   in_school = None
        reasons = ['可实习时长缺失', '每周到岗天数缺失', '是否成都线下缺失']
        恢复后 hard = {'passed': False, 'reasons': ['非在读']}   ← 被误淘汰
```

`in_school` 抽取本身不稳定（同一份文本重复抽取）：

```
raw     文本 -> {(None, 'master'): 1, (True, 'master'): 4}   ← 5 次里 1 次抽成 None
parsed  文本 -> {(True, 'master'): 5}
```

即约 10~20% 概率把在读候选人误判为「非在读」并直接淘汰，且**没有任何人工兜底**。

### 3. 为什么没顺手改成「缺失即放行」

另一种做法是「字段缺失时不因缺失而淘汰」（类似 `rules.yaml` 里院校层次
「非双一流一律 8 分，不得静默得 0 分」的口径）。但那会改变硬性条件语义，
超出用户本次的要求范围，故未实施，留作待定项。

## 测试失败分析（非本次改动引入）

```
FAILED tests/test_graph.py::test_bing_interrupts_then_resumes_to_80
FAILED tests/test_graph.py::test_yi_completes_with_80   ← 偶发，重跑即过
```

`test_bing_interrupts_then_resumes_to_80` 的失败与本次改动**无关**：

- 该用例的 resume payload 是
  `{days_per_week, chengdu_onsite, internship_duration_months}`，**不含 `in_school`**
- 一旦 `in_school` 抽成 `None`，恢复后硬性条件必然判「非在读」→ `score` 为 `None`
- **改动前同样会失败**：删掉的两个分支只是往 `reasons` 里多塞一条字符串，
  并不会把 `in_school` 补上，硬性条件照样淘汰

所以这是**既有的抽取不稳定 + 测试夹具不健壮**导致的偶发失败，
本次改动只是没有掩盖它。`test_yi_completes_with_80` 重跑即通过，属同一类抖动。

## 遗留风险

- `in_school` / `degree_level` 抽成 `None` 时会被静默淘汰，无人工兜底（见 #2）
- `test_bing_interrupts_then_resumes_to_80` 仍是脆弱用例，建议夹具补上 `in_school`（待定，未实施）
