# 2026-09-22 在读状态时间推导

## 背景

上一轮移除了「在读状态缺失」「学历层次缺失」的人工复核后，`in_school` 抽成 `None`
会被硬性条件直接判「非在读」淘汰，存在误淘汰风险。

用户提出：**是否在读可以用教育经历的时间信息判断**，例如「北京大学 2025.9-2028.6」
说明目前仍在读。相比让 LLM 直接给布尔值，时序比较是确定性的。

## 用户确认的口径

| 口径 | 选择 |
|---|---|
| 时间推导与简历文字明示矛盾时 | **A. 文字明示优先** |
| 完全抽不到时间信息时 | **B. 回退 LLM，仍为空则淘汰** |

两个口径合并后的优先级链（这是实现依据）：

```
1. in_school 非空（LLM 从原文读到的明示结论）→ 直接采用
2. education_end 可解析 → 与当前年月比较，end >= 当前月 → 在读
3. 都拿不到 → 非在读（淘汰）
```

第 1 条必须优先，否则会误伤甲：它写着「2023 级硕士研究生（在读），
**预计 2026 年 6 月毕业**」，按今天（2026-09-22）推已过期，但原文明确声明在读。
若让时间优先，甲会从 105 分「推荐」直接掉成「非在读」淘汰。

## 变更范围

| 文件 | 变更 |
|---|---|
| `app/graph/state.py` | `ExtractedFields` 新增 `education_end`（教育经历中最晚的结束时间，格式 `YYYY-MM`） |
| `app/tools/extract_tools.py` | 提示词新增第 8 条抽 `education_end`（原 8-12 条顺延为 9-13）；`_JSON_PROMPT` 的键列表同步 |
| `app/services/rule_engine.py` | 新增 `_parse_year_month()` 与 `resolve_in_school()`；`run_rules()` 的硬性条件由 `not fields.get("in_school")` 改为 `not resolve_in_school(fields)`；模块 docstring 补充说明 |
| `tests/test_rule_engine.py` | 新增 17 个用例（优先级、时间兜底、边界月、格式容错、解析失败、两个 `run_rules` 集成用例） |

## 关键决策

### 1. `education_end` 取「最晚的结束时间」，而不是起止区间

多段学历只需最晚的那个结束时间就能判断在读，不需要引入时间段列表
（那会顺带影响院校层次的多学历判定，属另一件事）。甲的例子：本科已结束、
硕士 2026-06 结束 → 取 2026-06。

### 2. 用字符串 `YYYY-MM` 而不是日期类型

LLM 抽取日期类型容易出格式问题；`YYYY-MM` 字符串配合宽松正则解析更稳，
解析失败一律视为「拿不到」，走下一级兜底。

### 3. `_parse_year_month()` 宽容解析

正则 `(\d{4})\D{0,4}(\d{1,2})?`，兼容 `2028-06` / `2028.06` / `2028 年 6 月` /
`2028/6` / 只有年份的 `2028`（月份缺省取 1）。月份非法（如 `2028-13`）时回退到 1 月。

### 4. 结束月等于当前月算在读

`end >= (今天年, 今天月)`，即「本月毕业」仍视为在读，避免月初把当月毕业的人误淘汰。

### 5. 不改提示词里 `in_school` 的语义

`in_school` 仍表示「简历是否明示在读状态」，时间推导是它的兜底，不是替代。
两者职责分离，冲突时明示优先 —— 与院校层次「名单权威 + LLM 校验」的思路不同，
这里刻意反过来：**文字明示是权威**，因为它是候选人的自我声明。

## 已验证

- `pytest tests/test_rule_engine.py` → **39 passed**（原 22 + 新增 17）
- 三份样例真实抽取：

  | 样例 | `in_school` | `education_end` | `resolve_in_school` |
  |---|---|---|---|
  | 甲 | True | `'2026-06'` | True |
  | 乙 | True | None | True |
  | 丙 | True | None | True |

  甲能从「预计 2026 年 6 月毕业」正确抽出 `2026-06`。
- 全图跑甲 → `hard_filter.passed=True`、`final=105`、`推荐进入笔试`，**未被时间规则误伤**

## 残留问题（未解决）

### 1. 乙、丙这类「无日期」简历仍然会偶发误淘汰

实测连续跑 4 次乙：

```
run1: in_school=True  degree_level=master  education_end=None  → 80 分
run2: in_school=True  degree_level=master  education_end=None  → 80 分
run3: in_school=None  degree_level=None    education_end=None  → 淘汰（误判）
run4: in_school=True  degree_level=master  education_end=None  → 80 分
```

两个结论：

- `in_school` 与 `degree_level` 是**同一次运行里一起抽空**的，不是各自独立抖动
  （说明是整批抽取质量下降，可能走了 JSON 回退路径）
- 乙、丙的简历只有「2024 级硕士研究生（在读）」，**没有任何日期**，
  所以时间兜底对它们完全无效 —— 约 1/4 概率被误判为「非在读」淘汰

按用户口径 B（仍为空则淘汰），这是已知且接受的代价。
若要消除，需要另定口径（例如把「2024 级」按学制推算毕业时间，或缺失时放行）。

### 2. `test_yi_completes_with_80` 偶发失败

同一根因：`in_school` / `degree_level` 同时抽空时 `score` 为 `None`。
该用例断言的是精确抽取结果，因此天然脆弱，非本次改动引入。

## 遗留风险

- 无日期简历的偶发误淘汰（见上）
- `education_end` 的抽取本身也可能抖动，但它的失效是「降级到下一级兜底」，
  不像 `in_school` 那样直接决定淘汰，风险较低
