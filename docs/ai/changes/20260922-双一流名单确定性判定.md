# 2026-09-22 院校层次改为双一流名单确定性判定

## 目标

原实现让 LLM 直接输出院校层次（`school_tier`），实测**同一提示词对同一份简历连续抽取会给出不同结果**（甲：`double_first_class` / `None` / `None`），导致同一候选人分数在 105 与 93 之间跳变。

改为：**LLM 只负责抽校名，层次由本地双一流名单做确定性匹配**，并在名单结论与 LLM 判断不一致（或两边都拿不到结论）时转人工复核。

## 用户确认的三个口径

| 口径 | 选择 | 落地方式 |
|---|---|---|
| 多学历算谁 | **A：任一段双一流即算** | 提示词分别抽本科院校 + 研究生院校；`_SCHOOL_FIELDS` 任一命中即算 |
| 名单未命中时怎么兜底 | **C：不一致或都拿不到 → 转人工复核** | `resolve_school_tier()` 返回 `review_reason`，`validate_node` 据此中断 |
| 包含匹配要不要开 | **不开** | 只做归一化后的精确匹配 + 别名表匹配 |

## 关键决策与踩坑

### 1. 判定表（`resolve_school_tier` 的唯一真源）

| 名单命中 | LLM 结论 | 计分 tier | 复核 |
|---|---|---|---|
| 命中 | 双一流 | `double_first_class` | 否 |
| 命中 | 非双一流 | `other` | **是（冲突）** |
| 命中 | 无结论 | `double_first_class` | 否 |
| 未命中 | 双一流 | `other` | **是（冲突）** |
| 未命中 | 非双一流 | `other` | 否 |
| 未命中 | 无结论 | `other` | **是（无法确认）** |

`fields["school_tier"]` 存在时视为**人工复核结论，优先级最高**（`other` / `double_first_class` 直接返回，不再复核）。

### 2. 刻意不做包含匹配

`is_double_first_class()` 只做「归一化 → 精确匹配 → 别名匹配」。
若开包含匹配，「四川大学锦江学院」会误命中「四川大学」。**这是有意的精度取舍，不要为了兜 LLM 抽脏而改成 `in`。**

归一化只做三件事：去括号内容（如「（在读）」）、去空白、去首尾标点。**不剥离专业名**——若 LLM 把校名抽成「电子科技大学计算机科学与技术专业」，会走「名单未命中 + LLM 判双一流」→ 冲突 → 人工复核，这是预期行为。

### 3. `rules.yaml` 的 `school_tier.unknown` 保留但已不可达

`resolve_school_tier()` 只返回 `double_first_class` / `other`，`unknown` 不再出现。
`rules.yaml` 未改动（v1.0 已冻结），该键留着无害。

### 4. 复核触发面扩大是口径 C 的必然代价

LLM 的 tier 判断本身不稳定 + 名单只覆盖 147 所，因此：
- 名单外院校（绝大多数）只要 LLM 判了「其他」→ 不复核（正常路径）
- 名单外院校 + LLM 未给结论 → 复核
- 校名抽取带杂质 → 复核

实测中「院校层次判定冲突」与「院校层次无法确认」两种原因都真实出现过。

## 已验证

- `pytest` → **18 passed**（需 `DASHSCOPE_MODEL=qwen-plus`，见「已知环境问题」）
- `npm run typecheck` / `npm run build` → 通过
- HTTP 全链路：
  - 乙（成都信息工程大学）→ `COMPLETED` 80 分（名单未命中 + LLM 判非双一流 → 不复核，院校 8 分）
  - 丙 → `WAITING_REVIEW`（时长/天数/线下三项）→ `/resume` → `COMPLETED` 80 分
  - 构造冲突样本（本科「清华大学深圳国际研究生院」）→ `WAITING_REVIEW`，原因仅「院校层次判定冲突：抽取结果为双一流，但名单未命中」→ `/resume` 带 `school_tier: "other"` → `COMPLETED` 93 分，`score.school == 8`（**人工覆盖生效**）
- 浏览器界面：复核弹窗仅渲染「院校层次」一项，`Segmented` 可选「双一流 / 非双一流」，提交后得 93 分 / 推荐进入笔试，console 无报错

## 已知环境问题（非本次引入）

### 1. `backend/.env` 的 `DASHSCOPE_MODEL=qwen3.8-max` 不存在

DASHSCOPE 返回 `400 InvalidParameter: url error`。**未擅自修改 `.env`**，需用户自行改回 `qwen-plus`；临时验证用环境变量覆盖（`load_dotenv` 不覆盖已有环境变量）。

### 2. `degree_level` 抽取非确定性 → 甲有约 1/6 概率被复核

实测甲（电子科技大学）连跑 6 次：5 次 `COMPLETED` 105 分，1 次 `WAITING_REVIEW` 且原因为「学历层次缺失」（LLM 把 `degree_level` 抽成 `null`）。
**与本次改动无关**——6 次中院校相关复核原因一次都没出现，原 `school_tier` 不稳定的问题已由名单消除。
但 `test_jia_completes_with_105` 仍因此存在偶发失败风险。
