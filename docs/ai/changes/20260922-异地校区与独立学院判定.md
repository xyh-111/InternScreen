# 2026-09-22 双一流异地校区 / 独立学院判定

## 目标

上一轮把院校层次改成双一流名单精确匹配后，暴露两个问题：

1. **「清华大学深圳国际研究生院」被误报冲突转人工复核** —— 它是清华的异地办学机构，合法双一流，但全名不在名单里
2. **「四川大学锦江学院」的正确结果纯属侥幸** —— 它是挂靠川大的独立学院（非双一流），LLM 若判双一流就会误报冲突

按用户给出的区分规律补齐「双一流校名 + 后缀」判定。

## 用户确认的口径

| 口径 | 选择 |
|---|---|
| 正向规则 | 「城市名 + 办学机构词」→ 判双一流 |
| 反向规则 | 后缀含「学院」→ 判独立学院（非双一流） |
| 城市清单 | **不建清单**（不新建 `cities.yaml`） |

## 关键决策与踩坑

### 1. 顺带修掉一个既有归一化缺陷（必须修）

原 `normalize_school()` 无条件剥离括号内容，导致名单里带括号的校名匹配失败：

| 校名 | 原归一化结果 | 原是否命中 | 修复后 |
|---|---|---|---|
| 中国石油大学（华东） | 中国石油大学 | **否** | 是 |
| 中国地质大学（武汉） | 中国地质大学 | **否** | 是 |
| 中国矿业大学（北京） | 中国矿业大学 | 是（侥幸，名单里恰好有「中国矿业大学」） | 是 |

前两所高校的候选人此前每次都会被判「名单未命中 + LLM 判双一流 → 冲突」→ 无谓复核。

**修法**：归一化保留括号，`classify_school()` 依次尝试「保留括号」与「剥离括号」两种形式精确匹配。
副产品：「哈尔滨工业大学（威海）」这类括号式异地校区走精确匹配命中，不依赖后缀规则。

### 2. 判定顺序与最长前缀

```
1. 归一化（去空白/首尾标点，保留括号）后精确命中名单 → 双一流
2. 剥离括号后精确命中名单 → 双一流
3. 别名表命中 → 双一流
4. 以某双一流校名为前缀时看后缀：
   含 campus_suffixes → 双一流（异地校区 / 研究生院）
   含 college_suffixes → 非双一流（挂靠的独立学院）
   都不含 → 无结论
5. 其余 → 无结论
```

- 前缀取**最长匹配**（`max(..., key=len)`），避免「中国矿业大学」抢先匹配「中国矿业大学（北京）」
- `campus_suffixes` 先于 `college_suffixes` 检查（更具体的办学机构词优先）
- **仍不做任意位置的包含匹配**——「四川大学锦江学院」不是被当成「四川大学」命中的，而是由「学院」后缀规则判为独立学院

### 3. 刻意不改 LLM 提示词

如果把「后缀含学院即独立学院」也写进 `EXTRACT_PROMPT`，LLM 的层次判断就与本地规则**同源**，
「名单 vs LLM」的一致性校验将失去独立性——校内学院假阴性（见 #4）就再也兜不住了。
保持 LLM 独立判断才能构成交叉验证。

### 4. 已知假阴性：校内学院会被判为非双一流

「北京大学光华管理学院」「上海交通大学医学院」「浙江大学竺可桢学院」后缀含「学院」，按规则判 8 分。
**依赖 LLM 冲突校验兜底**：LLM 判 `double_first_class` 时会转人工复核（`reasons` 含「名单判定为独立学院」）。
若实际简历中高频出现，缓解手段是把这些全称加进 `aliases` 指向母体校名。

（「北京大学医学部」不受影响——`学部` 在 `campus_suffixes` 里。）

### 5. `resolve_school_tier()` 的不对称性必须保留

**名单是权威，LLM 只能补判「非双一流」，不能把名单未命中的校名抬成双一流。**
因此「未命中 + LLM 判双一流」仍走冲突复核，而「判独立学院 + LLM 判双一流」也走冲突复核。

完整判定表（9 行）：

| list | llm | tier | 复核 |
|---|---|---|---|
| 命中双一流 | 双一流 | double_first_class | 否 |
| 命中双一流 | 非双一流 | other | 是（冲突） |
| 命中双一流 | 无结论 | double_first_class | 否 |
| 判独立学院 | 双一流 | other | 是（冲突） |
| 判独立学院 | 非双一流 | other | 否 |
| 判独立学院 | 无结论 | other | 否 |
| 未命中 | 双一流 | other | 是（冲突） |
| 未命中 | 非双一流 | other | 否 |
| 未命中 | 无结论 | other | 是（无法确认） |

`fields["school_tier"]` 存在时视为人工复核结论，优先级最高。

### 6. `is_double_first_class()` 直接删除

全仓库无调用方（`nodes.py` 只 import `resolve_school_tier, run_rules, validation_config`），
替换为三态 `classify_school()` 后不保留兼容包装。

## 附录：更正——`qwen3.8-max` 是存在的模型

### 背景

此前（`changes/20260921-初始搭建.md` §6 与 `changes/20260922-双一流名单确定性判定.md`）
记录为「`qwen3.8-max` 不存在」，依据是 `.env` 里的注释与 `400 InvalidParameter: url error` 的报错文案。
**这个结论是错的**，2026-09-22 实测推翻。

### 实测结果（同一 API key）

| 入口 | `qwen3.8-max` | `qwen3-max` | `qwen-plus` |
|---|---|---|---|
| 原生 SDK `dashscope.Generation.call` | **400 `InvalidParameter: url error`** | 200 | 200 |
| OpenAI 兼容 `https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions` | **200 OK** | 200 | 200 |
| 国际站 `https://dashscope-intl.aliyuncs.com/...` | 401（key 是大陆区，不适用） | 401 | 401 |

### 真实原因

`app/services/llm.py` 用 `ChatTongyi`，它走 DashScope **原生** `text-generation/generation` 服务。
`qwen3.8-max` 只在 **OpenAI 兼容模式**下提供，原生入口不路由该模型——
DashScope 按模型名解析服务地址，解析不到就报 `url error` 而非 `model not exist`。
**报错文案有误导性，不要据此推断模型不存在。**

### 三条出路

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 用上 `qwen3.8-max` | `get_llm()` 换成 `ChatOpenAI(model=..., api_key=..., base_url="https://dashscope.aliyuncs.com/compatible-mode/v1", temperature=0)` | 需新增 `langchain-openai` 依赖（当前未安装；`openai` 也未安装） |
| B. 留在 `ChatTongyi` | 只改 `.env`：`DASHSCOPE_MODEL=qwen3-max`（原生入口已验证可用） | 用不上 3.8 |
| C. 不改 | 验证时用环境变量覆盖 | 每次都要覆盖 |

> **后续**：用户选定方案 A，已实施。详见 `changes/20260922-DashScope兼容模式接入.md`。

### 教训

判断「模型不存在」前，至少要在**两个入口**各打一次真实请求，不要只看报错文案或 `.env` 注释。
