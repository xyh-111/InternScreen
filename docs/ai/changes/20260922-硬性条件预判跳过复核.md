# 硬性条件预判：确定性失败直接暂不推进，跳过复核

**日期**：2026-09-22
**涉及模块**：backend（rule_engine / graph.nodes / graph.routes）
**用户诉求**：一条硬性条件已确定性失败 + 另一条需要人工复核时，当前错误地推送到人工审核。应直接暂不推进，不走复核。

---

## 1. 根因

原流程：

```
parse → extract → validate_node（凑齐所有 review_reasons）
                      │
                      │ 只要 reasons.length > 0 → need_review=True
                      │ 不管硬性条件里有没有已确定判死的项
                      ▼
                 review_node（中断等人工）    ← 多余！
                      │ resume
                      ▼
                 screen_node → run_rules() → 第一次判硬性条件
                      ▼
                 硬性格拒 → 暂不推进（白走了一圈 review）
```

示例：
- `internship_duration_months = 2`（已抽到，< min=3 → **确定性失败**）
- 院校层次独立学院（名单 other、LLM 可能 double → **需要复核**）

原代码 `validate_node` 只看 `reasons.length > 0`，没跑硬性条件预判，所以命中了 `need_review=True` → 进 review。但这个简历在 `screen_node` 里无论如何都会被硬性格拒，review 完全浪费。

## 2. 修复方案

### 关键拆分：确定性失败 vs 字段缺失

原 `run_rules()` 把下面两种情况混成同一类判失败：
- `duration = 2`（**已抽到值**，但 < 3）→ 确定性失败
- `duration = None`（**字段缺失**，LLM 没抽到）→ 不确定，可能是简历没写，也可能就是不确定

两者应该不同处理：确定性失败 → 直接砍；字段缺失 → 走 review 让人工补。

### 新增 `precheck_hard()` 辅助函数

```python
def precheck_hard(fields: dict) -> dict:
    """预判硬性条件，区分「确定性失败」和「字段缺失」。"""
    return {
        "deterministic_failures": [...],   # 有值但不满足
        "missing_fields": [...],           # 值为 None
    }
```

- 共享同一份 `load_rules()` 配置 → 阈值永远与 `run_rules()` 一致
- 不做评级、不跑评分，只做预判分类 → 轻量

### 修改 validate_node

```python
precheck = precheck_hard(fields)
deterministic_failures = precheck["deterministic_failures"]
missing_fields = precheck["missing_fields"]

# 字段缺失仍列 reasons（等 review 补）
if "internship_duration_months" in missing_fields:
    reasons.append("可实习时长缺失")

# 最终路由判定
hard_already_failed = len(deterministic_failures) > 0
need_review = (not hard_already_failed) and len(reasons) > 0
```

注意：**确定性失败的原因不进 reasons 列表**，因为这些是"已确定判死"，不是"需要复核"。

### 修改 route_after_validate 优先级

```python
def route_after_validate(state):
    # 硬性条件已死 → 跳过 review，直接进 screen
    if state.get("hard_already_failed"):
        return "screen_node"
    if state["need_review"]:
        return "review_node"
    return "screen_node"
```

优先级：硬性格拒 > need_review > 正常通过。这样即便 reasons 里同时有"院校需要复核"和"duration=2 确定性失败"，也**只看 hard_already_failed**，直接进 screen_node。

## 5. 关键决策

1. **`precheck_hard` 与 `run_rules` 共享配置、不共享实现**：阈值从 `load_rules()` 取，但逻辑独立，避免后续改一个忘改另一个；同时 `precheck_hard` 不做院校层次（院校层次需要 resolve_school_tier 返回结论才知道，属于评分环节而非硬性条件环节）。
2. **确定性失败原因不进 reasons**：reasons 的语义是"需要复核的点"，不是"已死的点"。进 reasons 会在 review 弹窗里列出永远不可能通过的项，徒增人工困惑。
3. **route_after_validate 硬编码优先级**：`hard_already_failed` 必须**无条件**覆盖 `need_review`，不能用 `need_review and not hard_already_failed`——那是在 validate_node 里算好的结果，这里再表达一次是"保险"。
4. **不修改 run_rules()**：它继续做最终判定（含院校层次判定），`precheck_hard` 是前置预判，两者职责分离。

## 6. 残留

- 本轮没动前端，因为前端已经正确处理「rating=暂不推进」的情况；结果弹窗里的 `hard_filter.reasons` 会自然展示到底是"可实习时间不满3个月"还是其他。
- 如果以后想在 UI 上区分「是确定性拒单还是评分未达标」，可以给 `hard_filter` 加一个 `rejection_type` 字段。
